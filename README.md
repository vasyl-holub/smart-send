# Smart Sender — Webhooks

Тестове завдання Senior Frontend Engineer: вхід, список вебхуків і редагування.

**Стек:** React 19, TypeScript (strict), Vite, MSW, TanStack Query, React Router, React Hook Form,
Zod, shadcn/ui, Vitest.

## Запуск

```bash
npm install
npm run dev     # http://localhost:5173, мок-API (MSW) стартує разом із застосунком
npm test        # усі тести
```

Також є `npm run typecheck`, `npm run lint`, `npm run format:check` і `npm run build`.

**Тестові облікові дані:** `admin@smartsender.io` / `password123`

## Пріоритети

Спершу я робив те, що оцінюється, і в такому порядку:

1. **Ядро.** HTTP-клієнт із сесією та повторами, CSRF, мок за контрактом, обов'язковий тест.
   На цьому лежить головний ризик завдання.
2. **Сторінки.** Вхід, список зі станом в URL, редагування з помилками сервера біля полів.

Решту додано понад мінімум. Ядро від цього не залежить:

- перевірка відповідей схемами zod;
- UI на shadcn/ui;
- додаткові тести (усього 8, з них 2 UI-тести);
- Prettier і правила ESLint для імпортів.

## Структура

```
src/
  api/          транспорт і контракт API, без React
  features/
    auth/       стан сесії, дії (вхід / вихід / відновлення), сторінка входу, guard
    webhooks/   query-хуки, стан списку в URL, таблиця, модалка редагування
  components/   shadcn/ui та дрібні обгортки
  mocks/        MSW: стан у пам'яті та хендлери за контрактом
  app/          роутер, layout, провайдери
```

Залежності йдуть в один бік: `app → features → api`. Шар `api` не знає про React, тому найскладнішу
частину (сесію) тестують без рендерингу. Фічі та компоненти імпортуються через свої `index.ts`.

## Ключові рішення

### Сесія і повтори — `src/api/http-client.ts`

- **Один спільний rotate.** Усі запити, що одночасно отримали 401, чекають один проміс
  `/auth/token/rotate`. Потім кожен запит повторюється один раз.
- **Rotate не запускає rotate.** Auth-ендпоінти викликаються з `auth: false`, тож 401 від них не
  обробляється як протухла сесія. Рекурсія неможлива за побудовою, без окремого прапорця.
- **Запізнілий 401 не запускає другий rotate.** Клієнт рахує покоління сесії. Запит пам'ятає, з яким
  поколінням він пішов. Якщо його 401 приходить після вже завершеного rotate, запит просто
  повторюється.
- **Завершення сесії.** Помилка rotate або повторний 401 очищують стан і кеш даних і ведуть на
  вхід. Адресу з `?page=&search=` при цьому збережено: після входу користувач повертається на ту
  саму сторінку.
  - Свідоме уточнення: мережева помилка під час rotate нічого не каже про сесію. Тому сесія
    лишається, а запит отримує `NetworkError`.
- **`device_session_token`** існує лише в локальній змінній функції входу: не в стані, не в сховищі
  і не в URL.
- **`fingerprint`** генерується один раз і зберігається в `localStorage`.
- **CSRF.** `GET /csrf` виконується перед першим запитом, і токен іде на POST і PUT. На 419 клієнт
  оновлює токен і повторює запит один раз. Якщо токен тим часом оновив інший запит, нового `/csrf`
  не буде.
- **Відновлення сесії.** На старті клієнт пробує `/v1/me`, бо справжній бекенд тримав би сесію в
  cookie. Мок втрачає стан після перезавантаження, тож тоді показується екран входу. Умова це
  дозволяє.

### Дані та стан

- **Відповіді перевіряються схемами zod.** Типи DTO виводяться з цих схем, тож `as T` немає.
  Відповідь, що порушує контракт, дає `UnexpectedResponseError` одразу на межі `api/`.
- **Дані з сервера** зберігає TanStack Query. Після збереження вебхука запис оновлюється в кеші, а
  списки перезавантажуються. Повторюються лише мережеві помилки: 401 і 419 уже обробив клієнт.
- **Сесія** — маленький стор на `useSyncExternalStore` зі станами
  `unknown | anonymous | authenticated`. Дії над сесією винесено окремо. `initSession()`
  викликається явно з `main.tsx`, а не під час імпорту модуля.
- **Список.** Сторінка й пошук зберігаються тільки в URL. Нова пошукова фраза скидає сторінку на
  першу. Пошук має debounce, щоб не засмічувати історію, і синхронізується з «назад» / «вперед».
- **Редагування** — дочірній маршрут `/webhooks/:id`. Модалку відкриває сам маршрут, тож закриття —
  це навігація. Список із параметрами лишається під модалкою.

### Форми й помилки

`applyServerErrors` розкладає `payload` відповіді 422 по полях форми. Помилки для полів, яких у
формі немає, і решта помилок показуються над формою. На клієнті перевіряється лише, чи поле не
порожнє. Правила валідації визначає сервер.

Список має окремі стани: скелетон під час завантаження, помилка з «Retry», порожній результат
пошуку, порожній список і сторінка поза діапазоном.

### Мок — `src/mocks`

Мок реалізує весь контракт і правила з умови:

- CSRF перевіряється першим;
- `X-Captcha-Token` обов'язковий;
- `device_session_token` одноразовий і прив'язаний до fingerprint;
- сесія живе 30 с; rotate повертає 400 до `issue` і після `revoke`;
- є валідація полів і 404;
- 27 вебхуків, стан тільки в пам'яті.

## Тести

- **`src/api/http-client.test.ts`** (Node + MSW). Обов'язковий сценарій: два паралельні запити
  отримують 401, далі один rotate і успішні повтори. Також перевіряються:
  - невдалий rotate;
  - запізнілий 401;
  - мережева помилка під час rotate;
  - повтор на 419;
  - відповідь, що порушує контракт.
- **`src/app/app.test.tsx`** (jsdom + Testing Library). Застосунок рендериться цілком:
  - deep link із параметрами списку переживає редірект на вхід;
  - помилка 422 з'являється саме біля поля URL.

Тести перевірено мутацією: без спільного rotate або з поламаним `applyServerErrors` вони падають.

## Що не зроблено / можна покращити

- **E2E-тестів (Playwright) немає.** Пошук, пагінацію, «назад» / «вперед», протухання сесії й
  вихід я перевіряв у браузері вручну.
- **Сесія між вкладками.** Вихід в одній вкладці не синхронізується з іншими (можна через
  `BroadcastChannel`).
- **Незбережені зміни.** Модалка не попереджає про них під час закриття.
- **Розмір бандла.** Основний чанк ~190 kB gzip. Наступний крок — ліниве завантаження маршрутів.
- **MSW у збірці.** Мок вмикається і в продакшн-збірці, бо в цьому застосунку він і є бекендом.
